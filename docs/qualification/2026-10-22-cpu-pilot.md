## Pixels runtime investigation

Two bounded, 120-second diagnostic runs profiled the unchanged benchmark. With
two compute threads, PLS fitting consumed about 82 seconds and activation
extraction about 22 seconds. With one thread, PLS consumed about 104 seconds;
that run reached fewer component iterations. These partial runs do not establish
full-runtime estimates or numerical parity, and do not justify changing threads.

The metric uses 25 PLS components across 10 cross-validation splits. Both full
qualification attempts exhausted the 30-minute limit without returning a score.
No score mismatch was observed because no completed score was available.

## Completed pixels run

A third fresh Conda build ran the same installed candidate revisions with a
90-minute diagnostic allowance. The existing reference-score test passed with
no skips: 2,269.86 seconds execution (37 minutes 50 seconds), plus 2.81 seconds
collection. Peak process-tree RAM was 11.23 GiB. All 25 PLS components and 10
cross-validation splits were retained; the score assertion was unchanged.

Tests ran offline with result caching disabled. All four installed wheels were
verified before and after execution. The worker stopped automatically after logs
were downloaded; EC2 confirmed it stopped. No GPU was used.

The official profile now allows 60 minutes, providing about 22 minutes of
headroom over this measured run while retaining the 32 GiB memory limit.
This is based on one completed run on the stated worker, not a guarantee for
slower hardware. The successful run used the diagnostic 90-minute manifest;
its measured duration fits the new 60-minute limit, which has not been rerun
separately. No scoring implementation changed.

Across these runs, all 37 selected checks have now passed. This is cumulative
evidence from separate environments and revisions, not one 37-test run. Other
profiles, CUDA and automatic environment creation by `score()` remain outside
this qualification.
