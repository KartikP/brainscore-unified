# A real DROID episode through UMI

One official DROID sample episode passed input mapping, action recording, saved
output replay, and an intervention/recovery check. It contains **119 steps** and
three RGB cameras. The policy was an **untrained test network**.

| Check | Result |
| --- | --- |
| Download and TFRecord checksums | Verified |
| Camera and robot-state mapping | All 119 steps |
| Policy calls and recorded actions | 119 each |
| Captured layer outputs | 119 |
| Saved action and target replay | Exact, with zero model calls |
| Fixed-observation intervention | Changes the action |
| Recovery after removing the intervention | Exact |
| Provider, robotics, and tool tests | 33 passed |

The new `DroidPolicy` helper accepts a caller-supplied policy with an `infer`
method. It copies camera/state inputs, excludes demonstration actions and rewards,
validates action chunks, and clears queued actions at reset. The policy owns
preprocessing, model loading, and random-state reset.

The action definition uses seven joint velocities and one gripper position from
the named `action_dict` fields. It does not use the seven-value top-level action.
Timestamps are inferred from a declared 15 Hz period, rather than measured.

This check establishes real-data transport and tool behavior. A trained DROID
checkpoint still needs direct-versus-UMI comparison in its supported environment.
Closed-loop task success and physical robot control require separate evaluation.
