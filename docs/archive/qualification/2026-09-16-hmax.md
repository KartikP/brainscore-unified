# HMAX compatibility findings

**Later upstream control:** the [clean master comparison](2026-09-16-hmax-master.md)
passes exactly for both mapped HMAX CPU cases. It supersedes this report's
recommendation to leave UMI compatibility blocked on missing historical logs.
The measurements below remain valid; the older published-score discrepancy
also occurs on current upstream and is tracked separately.

## Result and qualification boundary

The full fixed-layer HMAX diagnostic passes on the recorded macOS CPU profile.
Legacy and UMI adapter routes produce identical activation values, named
coordinate values and dtypes, raw scores and normalized scores for all eight
candidate C2 layers on 2,560 private images. Their presentation MultiIndex level
order differs between independent processes; the section below records this
legacy metadata limitation and the precise audit comparison.
Repeated public-set scoring on 3,200 images also reproduces every score exactly.

This qualifies the tested fixed-layer adapter behavior. The current normal HMAX
loader uses a shipped fixed region map. The diagnostic does not exercise the
automatic-selection fallback, reproduce the original production environment,
or qualify HMAX on CUDA. The historical support gate remains open until it has
an explicit resolution.

## The default map reproduces the April mismatch

HMAX ships a JSON map with V4 at `c2_0` and IT at `c2_2`. A direct normal-loader
check confirms that `load_model('hmax')` loads that map and never constructs
LayerSelection. The candidate wheels contain the identical map, as do the
existing interface branches inspected locally.

The current [public HMAX page](https://www.brain-score.org/model/vision/652)
also displays those layer commitments and eight visual degrees. This is current
metadata, not proof of the settings used to produce its older scores.

| Region | Shipped layer | Current private score | April recorded score | Highest private score among all eight candidates |
| --- | --- | ---: | ---: | ---: |
| V4 | `c2_0` | 0.032692957 | 0.032693 | 0.032692957 |
| IT | `c2_2` | 0.047452645 | 0.047453 | 0.049386653 |

Both mapped scores reproduce the April report to six decimal places. Every
candidate layer remains below the corresponding published reference. Within
this profile, changing which of these eight layers is chosen cannot reproduce
the published values. Automatic layer-search randomness does not explain the
observed default path, which uses a fixed map.

The April report's causal explanation is therefore unsupported. The older
published score still needs its original model/protocol and environment
provenance. Reproducing the previously recorded mismatch is evidence about
compatibility, not a reason to replace the historical reference silently.

## Metadata ordering and audit recovery

The first independent audit failed a strict whole-assembly comparison because
the presentation MultiIndex levels appeared in a different order. No activation
value, row order, named coordinate value or score differed. Existing legacy
`attach_stimulus_set_meta` constructs its index-level list from a Python set.
Two small synthetic calls in separate legacy-only processes reproduce the level
order difference when the Python hash seed changes; neither call uses UMI or
performs model inference. That legacy source file is unchanged from the
committed candidate.

The final audit checks all 32 named coordinates and index levels, including
values, dtypes, dimensions, missing-value positions and missing sentinel types
exactly. It then reorders only MultiIndex levels for the complete
assembly equality check. It never sorts rows, changes values or applies a
numerical tolerance. Raw cross-process MultiIndex level order is therefore not
qualified as exact. Named coordinate access and the tested scoring path match.

The original failed `controls-run.json`, `independent-audit.log` and first audit
script are retained. `audit-index-order-investigation.json` records the isolated
reproduction. `independent-audit.json` and `independent-audit-retry-execution.json`
record the completed exact-value audit and its recovery. This is an explicitly
scoped comparison, not a claim that the first audit passed unchanged.

## Runtime repairs

Four HMAX-specific defects were reproduced and repaired:

1. Importing HMAX no longer disables the process-wide default HTTPS certificate
   checks. The real public patch file was retrieved with verification enabled.
2. Model construction now verifies the declared patch SHA1. The shared legacy
   `load_weight_file` function documents its SHA1 argument as deprecated and
   does not enforce it, so HMAX now checks explicitly before constructing a model.
3. Activation extraction preserves an existing global cache-disable setting,
   includes the current activation namespace, and restores the caller's exact
   environment value after success or failure.
4. Temporary forward hooks are removed after success, invalid layer lookup or
   inference failure, while pre-existing hooks remain attached.

The old implementation failed 12 of the 13 new runtime checks. After repair,
all 57 selected vision tests pass, including those 13 checks. The four-repository
validation runner now includes them. A real-image before/after probe preserved
all eight C2 layer outputs exactly. A two-image probe also matched legacy,
adapter and session paths exactly. The full-data comparison covers legacy and
adapter routes, not full-data session execution.

No weights, preprocessing, forward equations, PLS settings or numerical
acceptance thresholds were changed. These follow-up source changes are separate
from the 16 committed candidate changes and their already qualified wheels.

The HMAX cache guard still uses a process-wide environment setting. The tested
concurrent runs use separate processes. This evidence does not qualify
overlapping HMAX calls in different threads, even with separate model instances.

A separate local vision wheel also passes all 13 HMAX runtime checks, normal
model loading with the shipped map, and `pip check`. All 4,277 packaged files
match the working source. Its SHA256 is
`7f94e26cd983503bf020b026dde3775ad94f15ad832f3dc5cfbc2b2987be28c4`.
It was built with setuptools 79.0.1, within vision's declared `>=65.0.0` range,
and installed into an isolated target using the existing cold environment's
dependencies. This is not a fresh dependency installation or a separate full
scientific rerun from that wheel. The original qualified wheels and environment
remain unchanged, and the new wheel has not been published.

## Remaining compatibility work

No original scoring-job logs or archived production environment were available
for this review. The recommended release disposition is to preserve the
historical references, document the reproducible current fixed-map CPU profile,
and keep reproduction of those older published scores outside the qualified
claims. A release owner should accept that explicit support boundary before
promoting HMAX. The follow-up runtime changes have their own local wheel checks
and remain separate from the previously qualified wheel set.

Recover the original selected layers, checkpoint and software/data identities
for the published HMAX scores, or explicitly define a newly versioned supported
protocol after review. Exercise the complete automatic path if that behavior
is offered as supported. Keep the historical fixture values and failure status
until evidence supports changing the compatibility verdict.

The fixed ResNet18/GPT-2 CPU and L4 qualifications remain valid for their
recorded candidate. See the [committed candidate evidence](2026-09-16-candidate.md).
